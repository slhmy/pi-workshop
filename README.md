# Pi Workshop

Pi Workshop is a self-hosted conversation UI and autonomous container for the
[Pi coding agent](https://github.com/earendil-works/pi). A small, fixed Node.js
control plane runs Pi in RPC mode, streams its events to the browser, and serves
a persistent workspace in which Pi has broad engineering autonomy.

## Quick start

Create the runtime configuration and start the published image:

```sh
git clone https://github.com/slhmy/pi-workshop.git
cd pi-workshop
cp .env.example .env
chmod 600 .env
# Add the API key for the selected provider to .env.
docker compose up -d
```

Open <http://127.0.0.1:3000>. The named `pi_workshop_pi_data` volume stores the
mutable UI, Pi configuration, and sessions. Its initial contents are copied
from the image; later image upgrades do not overwrite an evolved workspace.

The equivalent direct command is:

```sh
docker run -d --name pi-workshop \
  --restart unless-stopped \
  --init --read-only --cap-drop ALL \
  --security-opt no-new-privileges \
  --tmpfs /tmp:size=256m,mode=1777 \
  -p 127.0.0.1:3000:3000 \
  -v pi-workshop-data:/agent-data \
  --env-file .env \
  ghcr.io/slhmy/pi-workshop:latest
```

## Evolve with Git

To let Pi evolve a checked-out repository rather than the image-seeded named
volume, bind mount the clone as its workspace and keep configuration and
sessions in separate volumes:

```sh
docker run -d --name pi-workshop-dev \
  --init --read-only --cap-drop ALL \
  --security-opt no-new-privileges \
  --tmpfs /tmp:size=256m,mode=1777 \
  -p 127.0.0.1:3000:3000 \
  -v "$PWD:/agent-data/workspace" \
  -v pi-workshop-config:/agent-data/config \
  -v pi-workshop-sessions:/agent-data/sessions \
  --env-file .env \
  ghcr.io/slhmy/pi-workshop:latest
```

Pi may change the entire repository, create additional applications and
services, install dependencies, and evolve its own settings, skills,
extensions, and user-installed runtime. The active control plane comes from the
image under `/opt/pi-control`; changes to `control/` require rebuilding the
image.

## Configuration

Set `PI_PROVIDER`, `PI_MODEL`, and the corresponding provider credential. Pi's
supported providers and custom `models.json` format are documented upstream.
`PI_ALLOWED_HOSTS` is a comma-separated allowlist used for every browser and API
request. Keep the localhost defaults for direct use; add the public hostname
when deploying behind a reverse proxy.
Persistent paths are:

| Path | Purpose |
| --- | --- |
| `/agent-data/workspace` | Mutable Web UI and project instructions |
| `/agent-data/config` | Pi settings, models, skills, and extensions |
| `/agent-data/sessions` | Conversation history |

The service exposes these endpoints:

| Endpoint | Purpose |
| --- | --- |
| `GET /healthz` | Container health |
| `GET /api/events` | Pi RPC events over SSE |
| `GET /api/state` | Current session state |
| `GET /api/messages` | Active conversation |
| `POST /api/prompt` | Send or queue an instruction |
| `POST /api/abort` | Abort current work |
| `POST /api/new-session` | Start a new session |

## Security

The bundled Compose file binds only to loopback. The control API intentionally
has no built-in user authentication; put an authenticated reverse proxy in
front of it before any remote exposure. The recommended container settings run
the process as the unprivileged `node` user with a read-only image filesystem,
dropped capabilities, and no Docker socket. The persistent `/agent-data` volume
remains writable, is first on the user tool `PATH`, and can contain an alternate
Pi installation for the next restart.

Pi has full read/write and shell access inside `/agent-data`, plus outbound
network access. Provider credentials are available to the Pi process. Use a
dedicated, quota-limited API key and do not mount unrelated host directories.

The image runs as UID 1000. Ensure a bind-mounted checkout is writable by that
UID. On SELinux hosts, add the appropriate `:Z` or `:z` relabel option after
reviewing how the checkout is shared.

## Development

Build and run the local image:

```sh
docker build -t pi-workshop:dev .
docker run -d --name pi-workshop-dev -p 127.0.0.1:3000:3000 \
  --env-file .env \
  pi-workshop:dev
```

Run the smoke test inside a running container:

```sh
docker exec pi-workshop-dev node /opt/pi-control/acceptance.mjs \
  http://127.0.0.1:3000
```

Images are published for `linux/amd64` and `linux/arm64` at
`ghcr.io/slhmy/pi-workshop`. `latest`, Git tag, and short commit SHA tags are
generated by the release workflow.
